# 設計書：ホームページのオンライン編集機能

作成日：2026-09-23
対象リポジトリ：`FSakai1997/fumiyasakai.github.io`（GitHub Pages、`main` ブランチ）

---

## 1. 目的と背景

### 現状の問題

1. ニュースを更新するたびに `news.html`（57KB、記事37件）を手元のエディタで直接書き換え、git push している。タグの閉じ忘れでページが壊れるリスクが常にある。
2. 同じニュースが `news.html` と `script.js` の配列に**二重に書かれている**。片方だけ更新すると、トップページと一覧ページの内容が食い違う。
3. PCが手元にないと更新できない。
4. 将来的に英語版を作る際、現在の構造では日本語HTMLを丸ごと複製することになり、二重管理がさらに増える。

### ゴール

- ブラウザからニュースとCVを追加・編集・削除でき、保存すると公開サイトに反映される。
- 情報源を一本化し、トップページと一覧ページの不一致を構造的に起こらなくする。
- 英語版を後から追加できる構造にしておく（今回は日本語のみ運用）。
- GitHub Pages のまま、追加のサーバーや費用なしで実現する。

### 今回やらないこと（意図的な除外）

- `research.html` のデータ化（更新頻度が低く、手元編集で足りる）
- 英語版ページそのものの作成（データ構造だけ先に用意する）
- 静的HTMLの自動生成パイプライン（GitHub Actions）
- 記事の全文検索、タグ絞り込みUI、RSS配信

## 2. 方式の決定と根拠

### 決定1：認証は GitHub の Fine-grained Personal Access Token に委ねる

GitHub Pages は静的ホスティングであり、サーバー側でパスワードを検証できない。HTMLやJSにパスワードを書く方式は、ページのソースを読めば突破できるため、認証として機能しない。

そこで「管理ページ自体は誰でも開けるが、保存操作は GitHub のトークンを持つ人しかできない」という形をとる。認証の実体を GitHub に委ねることで、追加サーバーなしに本物のアクセス制御が成立する。

**採用しなかった案**

- *Decap CMS + GitHub OAuth*：ログイン体験は優れるが、OAuth 中継サーバー（Cloudflare Worker 等）の運用か、ホスティングの Netlify 等への移行が必要。個人サイトの更新のために維持する負担に見合わない。
- *GitHub Issue + Actions*：認証コードが不要な点は魅力だが、既存記事の編集が困難でプレビューもない。

### 決定2：ページはブラウザ側でJSONから組み立てる

記事データを `data/news.json` と `data/cv.json` に移し、各ページが読み込み時に取得して描画する。ビルド工程がないため、保存した内容が即座に反映され、後から自分で手を入れやすい。

**トレードオフ**：JavaScript を無効にした環境では記事が表示されない。検索エンジンは JavaScript を実行するため実害は小さいが、ゼロではない。将来 SEO を重視する必要が生じた場合は、JSON が既に単一の情報源になっているため、GitHub Actions で静的HTMLを生成する方式へ移行できる。

## 3. データ構造

### 3.1 `data/news.json`

```json
{
  "schemaVersion": 1,
  "items": [
    {
      "id": "2026-09-16-gpl-coauthor",
      "date": "2026-09-16",
      "tag": "Publications",
      "draft": false,
      "ja": {
        "title": "共著論文がGPLで出版されました",
        "body": "<p>研究室の後輩であった竹下君との共著論文が<i>Geochemical Perspectives Letters</i>にて出版されました。</p>"
      },
      "en": { "title": "", "body": "" },
      "image": { "src": "image/SP_award_cut.JPG", "alt": "SP8Award", "width": "75%" },
      "citations": [
        {
          "text": "Takeshita, J., Hirose, K., …, <i>Geochemical Perspectives Letters</i>, 41, 53-57, 2026.",
          "links": [{ "label": "論文を見る", "url": "https://doi.org/10.7185/geochemlet.2633" }]
        }
      ]
    }
  ]
}
```

**設計判断**

- `body` は HTML 文字列として持つ。既存記事が `<i>` `<strong>` `<br>` と複数段落を使っており、プレーンテキストでは表現できないため。管理画面ではライブプレビュー付きで編集する。
- `date` は `YYYY-MM-DD` で保持し、表示時に `2026.09.16`（一覧）／`2026年9月16日`（トップ）へ整形する。現在この2形式が手書きで併存しており、整形を1箇所に集約することで表記ゆれを防ぐ。
- `id` は記事の同一性を保つためのキー。日付を変更しても参照が壊れないよう、日付とは独立に扱う（初期値は日付＋スラッグから生成）。
- `image` は任意。`null` なら画像なし。
- `draft: true` の記事は公開ページに出さない。書きかけを保存しておける。
- `items` は日付の新しい順で保持する。並び順はファイル内の順序で決まり、描画側でソートし直さない（手動で順序を入れ替えられるようにするため）。

### 3.2 `data/cv.json`

```json
{
  "schemaVersion": 1,
  "profile": {
    "ja": { "name": "坂井 郁哉 (Fumiya Sakai)", "lines": ["東京科学大学理学院 地球惑星科学系", "…"] },
    "en": { "name": "", "lines": [] }
  },
  "sections": [
    {
      "id": "education",
      "heading": "Education",
      "type": "dated",
      "entries": [
        { "date": "2023.04 - 2026.03", "ja": "東京大学大学院理学系研究科 …", "en": "" }
      ]
    },
    {
      "id": "publications",
      "heading": "Publications",
      "type": "numbered",
      "entries": [
        { "date": "", "ja": "Takeshita, J., … <a href=\"https://doi.org/…\" target=\"_blank\">[DOI]</a>", "en": "" }
      ]
    }
  ]
}
```

**設計判断**

- セクションの型は `dated`（日付＋内容の2列）と `numbered`（連番リスト）の2つだけ。既存CVの12セクションはすべてどちらかに収まる。
- 見出し（`heading`）は既に英語表記のため、多言語化しない。
- 全エントリが `ja` / `en` を持つ。`en` が空文字列なら `ja` にフォールバックする。Publications のような言語非依存の項目は `ja` に書いて `en` を空のままにすれば、英語版でもそのまま表示される。将来の翻訳作業を、本当に翻訳が要る項目だけに絞れる。

### 3.3 言語の扱い

`js/i18n.js` が言語を決定する：`?lang=en` クエリ → `localStorage.siteLang` → 既定値 `ja`。

描画関数は `pick(entry, lang)` を通して文字列を取り出し、指定言語が空なら `ja` へフォールバックする。**今回は英語ページも言語切替ボタンも作らない**が、この関数を通しておくことで、後から英語版を追加する際にデータ構造とレンダラを変更せずに済む。

## 5. 管理画面の設計

### 5.1 画面の流れ

**画面1：ログイン**

トークン入力欄と「このPCに記憶する」チェックボックス。入力されたトークンで `GET /repos/FSakai1997/fumiyasakai.github.io` を呼び、`permissions.push` が真であることを確認してから次へ進む。トークンが無効な場合は、原因（期限切れ／権限不足／リポジトリ相違）を区別して表示する。

チェックあり → `localStorage`、なし → `sessionStorage`（タブを閉じると消える）。

**画面2：編集**

上部にタブ：`ニュース` / `CV` / `画像` / `ログアウト`。

**ニュースタブ**
- 記事一覧（日付・タグ・タイトル・下書きバッジ）
- 各行に `編集` `複製` `削除` `↑` `↓`
- `新規作成` ボタン
- 編集フォーム：日付、タグ（選択式＋自由入力）、タイトル（日本語／English 切替）、本文（HTMLテキストエリア）、画像、引用ボックス（可変個数）、下書きフラグ
- 右側に**ライブプレビュー**。公開ページと同じ `render-news.js` と `style.css` を使って描画するため、プレビューと本番が食い違わない。

**CVタブ**
- セクション選択 → エントリ一覧 → 日付・内容の編集、追加・削除・並べ替え

**画像タブ**
- ファイル選択 → `image/` 配下へアップロード → 記事から参照するパスを表示
- 既存画像の一覧表示

### 5.2 保存処理

1. 読み込み時に `GET /repos/{owner}/{repo}/contents/data/news.json` で内容と `sha` を取得し、`sha` を保持する。
2. 保存時に `PUT` で新しい内容と保持中の `sha` を送る。コミットメッセージは `content: update news (YYYY-MM-DD HH:MM)`。
3. `sha` が食い違う（HTTP 409）＝別の経路でファイルが変わっている。上書きせず、「別の場所から更新されています。再読み込みしてください」と表示して、利用者に判断を委ねる。
4. 成功したらコミットへのリンクと「1〜2分で公開に反映されます」を表示する。

### 5.3 事故を防ぐ仕組み

- JSON として妥当でなければ保存ボタンを押せない。
- 保存前に「何件が何件になるか」（例：37件 → 38件）を表示する。件数が大きく減る操作は意図しない削除の可能性が高いため、確認を挟む。
- 未保存の変更があるまま画面を離れようとしたら警告する。
- すべての保存が git のコミットとして残るため、GitHub 上からいつでも復元できる。

## 6. セキュリティ上の前提と限界

**正直に記しておくべきこと**

- 管理ページの URL は秘密ではない。リポジトリが公開されているため、`admin/` の存在は誰でも知り得る。これは「隠し扉」ではなく「鍵のかかった扉」であり、鍵の検証は GitHub が行う。
- トークンはブラウザの `localStorage`（または `sessionStorage`）に保存される。**共用PCでは「このPCに記憶する」を使わないこと。**
- トークンが漏れた場合、GitHub の設定画面から即座に失効できる。

**使用するトークンの条件**

- 種類：Fine-grained personal access token
- 対象リポジトリ：`fumiyasakai.github.io` **のみ**
- 権限：`Contents: Read and write` **のみ**
- 有効期限：1年（期限が切れたら再発行が必要。管理画面に残り日数を表示する）

この条件であれば、仮にトークンが漏れても影響範囲はこのサイトのファイル書き換えに限定され、他のリポジトリやアカウント設定には及ばない。

`robots.txt` で `admin/` をクロール対象外にし、`admin/index.html` に `<meta name="robots" content="noindex,nofollow">` を置く。これは検索避けであって、アクセス制御ではない。

## 7. 既存データの移行

### 手順

1. `tools/migrate_news.py` が `news.html` を解析し、`data/news.json` を生成する。標準ライブラリの `html.parser` のみを使い、追加インストールを不要にする。
2. `tools/migrate_cv.py` が `cv.html` を解析し、`data/cv.json` を生成する。
3. 生成物を検証する（下記）。
4. 検証が通ってから `news.html` / `cv.html` を描画型に書き換える。

### 検証方法

- **件数**：`news.json` の `items` が 37 件であること（現在の `<article class="news-card">` の数と一致）。
- **本文の保全**：移行前後で、HTMLタグを除去したテキストを比較し、完全一致すること。1文字でも失われたら移行失敗とみなす。
- **リンクの保全**：移行前の `news.html` に含まれる `href` をすべて抽出し、`news.json` 側に同じ集合が存在すること。
- **目視確認**：ローカルサーバー（`python -m http.server`）で描画し、現行ページと並べて比較する。特に画像付き記事（`PhD.jpg`、`SP_award_cut.JPG`、`AIRAPT_29.JPG`）と、引用ボックスが複数ある記事を重点的に見る。

移行前の `news.html` / `cv.html` は git の履歴に残るため、別途バックアップは作らない。

### 移行中に直る既知の不具合

`cv.html` の Lectures セクション（231〜243行目）で `<div class="cv-grid">` が閉じられていない。データ化により自動的に解消する。

## 9. 運用手順（利用者向け）

1. GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens で、上記6節の条件のトークンを発行する。
2. `https://fumiyasakai.github.io/admin/` を開き、トークンを貼る。
3. 編集して保存する。
4. 1〜2分後に公開サイトへ反映される。

この手順は `admin/index.html` 内にも記載し、外部の文書を見に行かなくても済むようにする。
